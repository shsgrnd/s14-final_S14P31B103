# 📖 DPO Annotation Guide for GitCat

`작성일:` 2026-05-11  
`작성자:` 팀원 A (Data Quality Owner)  
`목적:` SFT 모델 답변 중 사용자가 선호하는 '빠르고 정확한 해결책'을 선별하기 위한 기준 정의

---

## 1. 핵심 원칙: "The Minimalist Expert" (미니멀리스트 전문가)

사용자는 충돌 상황에서 AI의 장황한 설명을 듣고 싶어 하지 않습니다. AI는 **"어느 경로에서 무엇이 문제였고, 이렇게 고쳐라"**를 즉각적이고 정확하게 제시해야 합니다.

---

## 2. 선호 답변 (Chosen) 판단 기준

다음 항목 중 **3개 이상**을 만족하며, **필수 항목**을 준수한 경우 `Chosen`으로 분류합니다.

### ✅ 필수 항목 (Mandatory)
- **JSON 유효성**: 결과값이 유효한 JSON 형식이어야 하며, 파싱 오류가 없어야 함.
- **코드 무결성**: `merged_code` 내에 Git 충돌 마커(`<<<<<<<`, `=======`, `>>>>>>>`)가 남아있지 않아야 함.

### 🌟 가점 항목 (Preferred)
- **경로 및 컨텍스트 명시 (Contextual Locality)**: 첫 두 문장 내에 충돌 파일 경로와 함께, 어떤 로직(함수명, 모듈 등)에서의 충돌인지 구체적으로 명시함.
- **기술적 근거 제시 (Technical Rationale)**: 단순히 "A를 선택함"이 아니라, "의존성 라이브러리 버전 충돌 방지"나 "비즈니스 로직의 최신성" 등 엔지니어링 관점의 이유를 간결하게 포함함.
- **전문가적 톤 (Senior Authority)**: 시니어 개발자처럼 단호하되, 근거에 기반한 해결책 제시. (예: "~~로 병합하는 것이 안전합니다.")
- **코드 스타일 유지 (Style Consistency)**: 주변 코드의 인덴트(2칸/4칸), 따옴표 스타일(`'` vs `"`) 등을 파괴하지 않고 유지함.

---

## 3. 비선호 답변 (Rejected) 판단 기준

다음 항목 중 **1개라도** 해당하면 `Rejected`로 분류합니다.

- **기술적 할루시네이션**: 원본 코드에 없는 변수나 함수를 임의로 생성하여 병합 결과에 포함하는 경우. (가장 엄격하게 배제)
- **장황한 서론 및 중언부언**: "안녕하세요", "분석 결과" 등 핵심과 관계없는 문구로 답변의 시작을 늦추는 경우.
- **판단 유보 (Indecisiveness)**: "A와 B 중 선택할 수 있습니다"와 같이 사용자에게 최종 판단을 전가하는 경우.
- **문법 파괴 (Syntactic Error)**: 병합된 코드(`merged_code`)에서 중괄호(`{}`) 짝이 맞지 않거나, 기본 문법이 깨져 린트(Lint) 에러가 예상되는 경우.
- **경로 누락**: 어느 파일에서 발생한 충돌인지 언급하지 않고 코드만 제시하는 경우.

## 4. 자동 스코어링 로직 가이드 (For 팀원 C)

자동 생성 스크립트(`generate_dpo_candidates.py`) 작성 시 아래 가중치를 참고하십시오.

| 항목 | 가중치 | 검사 로직 예시 |
| :--- | :---: | :--- |
| **Path Match** | +40 | `case_path` 문자열이 `response`에 포함되는가? |
| **JSON Valid** | +30 | `json.loads()`가 성공하는가? |
| **Technical Reason** | +20 | '의존성', '최신성', '보안' 등 기술적 키워드가 포함되었는가? |
| **Length Penalty** | -20 | `len(explanation) > 400` 인가? (현업에선 더 짧은 것을 선호) |
| **Syntax Error** | -100 | 병합된 코드에서 기본 문법 에러가 발견되는가? |
| **Conflict Marker** | -100 | 답변 내에 `<<<<<<<` 문자열이 포함되는가? |
